# 홍보글 이의제기와 2차 복원 신청

## 운영 반영 순서

1. 운영자 확인 후 `supabase/migrations/0012_post_appeals.sql` 적용.
2. 기존 데이터 백필 없이 새 테이블 및 서버 전용 RPC 생성 여부 확인.
3. Next.js 빌드 및 사이트 Worker 배포. Threads Worker는 변경하지 않음.

SQL 적용 전 새 사이트 코드를 배포하면 제한된 글의 상태 조회 및 관리자 조치가 실패하므로 순서를 지킨다.

## 흐름

- 관리자 홍보글/신고 화면: 숨김·차단 사유 입력. 기본값 `내부 운영정책에 의한 숨김 및 차단`.
- 내 홍보 및 글 상세: 작성자만 이의제기 버튼과 사유, 검토 결과를 조회.
- 작성자는 글을 보완한 뒤 30~5,000자 설명을 제출. 대기 중 중복 접수 금지.
- `/admin/appeals`: 관리자 인증 후 복원 승인, 추가 보완, 2차 PDF 요청 또는 1차 비승인 처리.
- 추가 보완은 같은 1차 단계에서 재접수 가능. 비승인 또는 PDF 요청은 2차 단계이며 재이의제기 입력란과 버튼을 제거하고 서버에서도 재접수 금지.
- 2차 단계의 버튼은 `복원 신청하기`로 바뀌고 `/restoration?post=번호`로 연결.
- PDF 및 Word 양식 모두 제공. 타이핑 가능, 자필 불필요. 완성된 PDF와 증빙을 `support@thehongbo.com`으로 직접 첨부해 제출.
- 이메일 자동 수신/검증 기능은 없음. 관리자가 지원 메일에서 자료를 검토한 후 같은 관리자 화면에서 승인.
- 복원은 게시글 상태만 active로 바꿈. 만료 기간과 계정 차단을 자동 해제하지 않음.

## 데이터와 권한

`post_appeals`는 글마다 현재 사유·상태·본문·답변·버전·처리 이력을 저장한다. 사용자 입력은 공개 posts.extra에 저장하지 않는다. 테이블과 RPC는 anon/authenticated 권한을 차단하고 service_role만 사용한다. 서버 액션이 관리자 또는 작성자 인증을 수행하며, RPC도 작성자 ID 및 제한 상태를 검증한다.

글 행 잠금과 버전 검사를 통해 중복 접수 및 오래된 검토 화면의 결정을 막는다. 복원 승인 시 글의 updated_at도 비교한다. 삭제된 글에는 신청/복원이 불가능하다. 최초 적용 시 기존 제한 글은 기본 사유로 1차 접수 가능하며 기존 글을 일괄 변경하지 않는다.

## 검증

`npm test --prefix automation/threads`의 appeals.test.mjs가 PGlite에서 새 마이그레이션을 실행하고 1차/2차 전환, 타 작성자 거부, 중복 접수, 오래된 버전, 수정 후 승인 거부, 권한, 삭제 글 처리를 검증한다.

신청서 Word 소스는 `scripts/generate-restoration-form.py`로 생성한다. PDF는 해당 Word 양식을 렌더링해 생성했으며 5쪽 전체를 PDF 렌더러로 확인한다. 시스템에 Word/LibreOffice가 없을 때는 임시 docx-preview 및 Chromium 렌더러로 문서 배치를 확인할 수 있다.
